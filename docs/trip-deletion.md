# Trip deletion

Owners open Edit trip and choose the red Delete trip button inside that popup. A separate inline confirmation names the trip and explains the affected data; Keep trip cancels. New-trip drafts do not show deletion. Confirmation is required before any delete operation. Successful deletion returns to My trips and clears that trip's edit draft.

Connected deletion requires an authenticated session, internet access and no queued/pending/conflicted changes for that trip. The `delete_trip(uuid,bigint)` RPC checks ownership and the original trip version, takes the same advisory transaction lock as normal mutations, atomically tombstones the trip and all child entities, and revokes its invitations. Retries after a lost response return success without repeating version increments. A stale trip-settings version must be reopened before deleting. No existing trip data is deleted when installing migration 002; only confirming a trip deletion invokes it.

Deletion removes the trip from the application for all travelers, with no in-app restore. Records remain tombstoned in Postgres for offline conflict protection; this is not a physical database purge. Membership records and historical payloads remain available under the existing RLS policies, allowing deleted records to synchronize. It cannot erase already downloaded copies. The mutation RPC rejects new children, stale edits and receipt replay into a deleted trip. Invitation creation/acceptance and online service calls reject deleted trips. Personal-list checks still protect tombstone payloads. Deleted parents hide all children locally even if an old offline mutation is retained for conflict review.

The local demo marks only this browser's trip and child records deleted; it does not call the backend. Tests use disposable local/in-memory records. Private live trips were not deleted. Live two-account/browser verification remains deferred. The frontend is published through GitHub Pages; migrations 002/003 and the compatible backend service check are installed in the shared backend.

Verification covers confirmation/cancellation, returning to the library, preserving other trips, editor/viewer/outsider denial, stale-version rejection, invitation revocation, cascade tombstones, idempotent retry, offline-edit and receipt resurrection prevention, pending/offline deletion guards and remote deletion conflicts.
