# Smart schedule adjustments

Choose Adjust schedule from a daily itinerary. Select an activity to start from, set its start and duration when flexible, and optionally add a per-leg buffer or close later gaps. The preview keeps itinerary order. By default later flexible entries only move later; close gaps explicitly permits earlier starts. Fixed reservations and flights retain their original times, duration and order. Opening windows supplied by users are respected; unknown hours remain review notes. Multiday stays remain unchanged and their travel connections need separate review.

Saving an activity time/duration/end change or changing per-leg travel settings offers a Review schedule reminder. It does not silently move later entries. Duration edits in the activity form also update an existing explicit end/arrival time, including destination time zones and daylight-saving changes.

Travel uses explicit manual minutes first, then a matching in-memory Google route estimate, then labeled straight-line speed estimates when coordinates exist. Unknown or invalid legs block applying changes until the user provides minutes or fetches an estimate. Route requests are sequential so each leg uses the proposed preceding departure time; up to ten new route requests are made per click. Changing departure, origin, destination or transport invalidates that leg's live estimate. Google estimates remain in memory; manually entered leg overrides are saved with the itinerary. Google route availability, past-date restrictions, traffic and transit timetables can affect estimates. No optimality claim is made and activities are never reordered.

All calculations use zoned instants. Nonexistent/ambiguous DST inputs, midnight/date-boundary crossings, invalid durations/buffers, unavailable travel, missed fixed appointments and supplied closing-hour conflicts block Apply. Affected activities show before/after times in AM/PM. Cancel saves nothing. Limits: at most 40 single-day activities; no automatic splitting across dates or optimizing around a multiday flight/stay.

Applying uses a single IndexedDB transaction for the changed entries. The complete local day set and record versions are checked, including unchanged fixed entries. A new/edited/deleted local entry invalidates an old preview. Offline operations use distinct idempotent mutation IDs and monotonically ordered sequences. Shared synchronization still uses the existing per-record server authorization and compare-and-swap RPCs: it is not one server-side batch transaction. Remote edits discovered on reconnection can conflict or invalidate scheduling assumptions and need review through the existing sync/conflict UI. Live two-user verification remains deferred.

Verification covers cascading duration/start changes, manual travel overrides (including zero), buffers, fixed reservations/flights, explicit ends, multi-day exclusion, opening windows, unknown/stale routes, time zones, DST and midnight. UI tests cover preview/cancel/apply, viewer protection, stale-record checks and proposed departure routing. IndexedDB tests verify local all-or-nothing application, unchanged reservation guards, concurrent additions, offline queue order and lost-ack retries. An application-level demo test applies a schedule to actual local records and verifies fixed start times remain unchanged. No private production trip data is modified.
